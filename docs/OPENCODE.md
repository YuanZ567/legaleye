## 一、项目概述

### 1.1 项目信息
- 项目代号：**LegalEye 法眼**
- 一句话定位：面向**中国出海企业**（跨境电商 / SaaS / 数据驱动型互联网）的**数据合规智能审查多智能体系统**，用中心化编排的真多智能体协作，完成隐私政策 / 用户协议 / 数据处理协议（DPA）/ 数据出境标准合同（SCC）等合规文件的**单文件审查与多文件交叉一致性校验**，输出带法规条款可追溯引用、数据流知识图谱、整改 diff、跨文档矛盾检测的结构化合规报告。
- 目标用户：出海企业的**数据合规负责人（DPO / 法务 / 信息安全）**、跨境业务法务团队、服务出海客户的律所与咨询机构。
- 核心价值主张：将出海数据合规审查从"人工逐条对照法条 + 凭经验判断 + 多份文件分别审"升级为"**多智能体按 PIPL 合规维度并行分工 + 官方法规/国标/SCC 模板知识库对标 + 处罚案例风险锚定 + 数据流图谱合规推理 + 多文档交叉矛盾检测 + 结构化可追溯报告**"，实现省时、降漏、可审计、可整改、可闭环。
- 差异化定位：**通用 LLM 给不了可追溯性，法律软件给不了多智能体过程透明与图谱推理，出海企业既缺专业工具又缺本土化深度**——LegalEye 站在二者空白处。

### 1.2 项目目标
- **业务目标**：MVP 上线后，单份隐私政策审查产出结构化报告 < 3 分钟；隐私政策 + DPA + SCC 三份联合审查 < 10 分钟；每条合规结论附法规条款号引用与法规版本标注。
- **技术目标**：跑通"中心化编排 + 真多智能体（工具调用/反思/路由）+ 6 维度并行 + 多文档交叉校验 + 图谱合规推理 + 四块可视化 + 多模型切换 + 账号体系 + 国内轻量服务器部署"完整链路。
- **质量目标**：三层评估指标达标（见第十三章）：抽取层实体 F1 ≥ 0.85；结论层高风险召回 ≥ 90%、误报 ≤ 15%、条款引用准确率 ≥ 85%；多文档交叉矛盾检出率 ≥ 80%。
- **学习目标**：掌握 LangGraph 状态图与工具型 Agent、LangChain RAG 双知识库、React Flow 图谱与画布、Celery 异步任务、Docker Compose 部署、LLM 系统化评估方法论。

## 二、市场与业务背景（真实背景，非虚构）

### 2.1 监管环境：数据出境合规是出海企业绕不开的法定门槛
- 《个人信息保护法》（PIPL，2021-11-01 施行）、《数据安全法》（2021-09-01）、《网络安全法》（2017-06-01）构成"三法"。
- **数据出境三件套**（出海场景的法定必做项）：
  - 《数据出境安全评估办法》（2022-09-01 施行）：关键信息基础设施运营者或处理 100 万人以上个人信息的处理者出境，须申报安全评估。
  - 《个人信息出境标准合同办法》（2023-06-01 施行）：非触发安全评估的出境场景，须签订**官方标准合同（SCC）**并向网信办备案。
  - 个人信息保护认证（第 38 条第 2 项路径）。
- 执法真实且有标志性：某出行平台因过度收集个人信息、数据出境未依法申报等被处 **80.26 亿元**罚款（网信办，2022-07）；网信办、工信部对违规 App 的通报与处罚常态化公示。**合规从"可选"变为"出海准入条件"。**

### 2.2 出海企业的真实合规场景（痛点具象化）
| 场景 | 典型数据流 | 真实痛点 |
|---|---|---|
| 跨境电商独立站/平台 | 订单含收货人姓名、地址、电话出境至境外物流/支付 | 是否触发安全评估？是否需 SCC 备案？隐私政策与 DPA 说法是否一致？ |
| 出海 SaaS / 工具类 | 用户数据存储于境外云（AWS/Google），营销投放对接海外广告平台 | GDPR 与 PIPL 双法对标、跨境传输合法性基础、单独同意 |
| 海外应用商店上架 | 隐私政策需中英文且符合 Apple/Google 政策 | 隐私政策更新频繁，人工逐条对照法条耗时 |
| 集团内共享 | 境内总部与境外子公司共享用户数据 | 委托处理 vs 跨境提供的边界、共同处理责任划分 |

### 2.3 现状痛点（五条）
1. 合规审查依赖人工逐条阅读与个人经验，耗时长、易漏条款、难对标最新法规版本。
2. 文件中数据流向（谁收集、委托谁、共享给谁、是否出境）散落在长文本里，人工难以建立全局图谱，**跨境高风险路径最易被遗漏**。
3. 审查结论以批注/口头为主，无法规条款级引用，难复核、难审计、难对监管说明依据。
4. 隐私政策 / DPA / SCC **多份文件分开审，声明不一致（政策说出境、DPA 没写、SCC 缺失）无人交叉核对**——这是实践中最高频的合规漏洞。
5. 审查与整改割裂——发现问题后仍需人工起草修改文本，闭环慢；法规更新后历史报告无法自动感知影响。

### 2.4 多智能体方案价值
- **专业化分工**：每个审查智能体专注单一合规维度（随 PIPL 章节划分），prompt 精炼、知识聚焦，效果优于单 prompt 通吃。
- **并行加速**：合规维度天然正交，并行审查显著缩短耗时（联合审查场景收益更大）。
- **真工具化**：智能体主动检索法规库 / 处罚案例 / 数据流图谱，结论有据可依，非凭记忆生成。
- **结构化可追溯**：审查过程与结论均为结构化数据，每条结论带法规条款号与法规版本，支持复核与监管说明。
- **图谱化呈现**：数据流知识图谱将长文本中的实体关系显式化，**图上推理识别敏感数据出境可达路径**并高亮。
- **交叉校验**：多文档联合审查检测跨文档矛盾，发现人工单份审查发现不了的系统性漏洞。

## 三、目标用户与灯塔行业

### 3.1 主用户画像（单一真实主用户）
- **身份**：出海企业的数据合规负责人（DPO / 法务负责人 / 信息安全负责人），或服务出海客户的律所/咨询机构律师。
- **任务**：对新上线/改版的隐私政策、用户协议、DPA、SCC 进行合规审查；应对应用商店审核、监管问询、客户尽调。
- **痛点**：时间不足、法规更新追不上、多文件一致性无人核对、审查结论无法给监管方/客户展示依据。
- **决策链**：DPO 提出需求 → 法务/合规团队使用 → 安全/IT 提供部署与数据保障 → 老板关注成本与风险敞口。

### 3.2 灯塔行业：出海 / 跨境电商（MVP 聚焦）
选型理由（与竞品与创新点的咬合）：
1. **监管刚性最强**：数据出境三件套是法定必做，需求不是"想要"而是"必须"。
2. **场景最尖锐**：跨境数据流天然存在，数据流图谱与跨境审查维度直接命中核心痛点。
3. **创新点天然匹配**：SCC 官方标准合同比对（有真实标尺）、数据出境路径推理（有真实图）、多文档交叉校验（政策/DPA/SCC 不一致是真实高频）。
4. **市场基数大**：中国跨境电商 B2C 出口规模持续增长（阿里国际站、SHEIN、Temu、TikTok Shop 生态带动大量卖家与 SaaS 服务商），出海 SaaS 数量级达万家。
5. **可扩展**：MVP 先吃透"出境合规"单一核心，后续按行业（医疗/金融/汽车）与法域（GDPR 对标）扩展维度即可复用框架。

### 3.3 功能优先级随用户画像推导
| 用户诉求 | 对应功能 | 优先级 |
|---|---|---|
| 出境是否合规 | 跨境传输审查 + SCC 模板比对 + 安全评估触发判定 | P0 |
| 隐私政策合规 | 6 维度单文件审查 | P0 |
| 多文件是否打架 | 多文档交叉一致性校验 | P0 |
| 给监管/客户看依据 | 条款级可追溯引用 + 法规版本标注 | P0 |
| 怎么改 | 整改建议 + diff | P0 |
| 数据流到哪了 | 数据流知识图谱 + 出境路径推理 | P0 |
| 历史报告失效没有 | 法规变更自动重审 | P1（增强项第一顺位） |
| 对标欧盟 | GDPR 对标维度 | P2（增强项） |

## 四、竞品分析（v1.0 深化：补真实对标 + 对比矩阵）

### 4.1 六类竞品审视

**① 通用大模型直用（ChatGPT / Claude / 通义 / Kimi）**
- 不足：无法规 RAG 对标、无结构化合规报告、无过程透明、无审计追溯、上传敏感文件有数据外泄风险、无法规版本追踪、无多文档交叉。
- LegalEye 差异：法规知识库 + 工具型多智能体 + 条款级可追溯引用 + 图谱推理 + 原文不持久化 + 国内模型默认数据不出境。**不拼便利性，拼可审计性与整改闭环。**

**② 专业法律 AI（LawGeex / Kira / eBrevia；国内法大大、e签宝智能审查）**
- 不足：Kira 类英文法域为中心、需训练语料、不解释推理；国内多与电签套件捆绑、规则为主非 LLM、闭源不能 BYO 模型、合规维度不分立、无图谱推理。
- LegalEye 差异：**中国数据合规专域 + 出海场景**、多智能体按 PIPL 章节维度并行、过程与依据可视化、provider 可切。

**③ 隐私合规扫描器（App 代码级扫描类：奇安信/安恒相关产品）**
- 不足：聚焦 App 代码/SDK 采集行为扫描，**不审查合规文件文本本身**；隐私政策审查多为止步关键词匹配，无多文档交叉。
- LegalEye 差异：**文件级语义审查 + 数据流图谱 + 法规条款对标 + 多文档交叉**，填补"文件级合规审查"空白。

**④ 全球隐私管理平台（OneTrust / TrustArc / Termly / iubenda）**
- 不足：**以欧美法域与 GDPR/CCPA 为中心，中国法与出海企业落地深度不足**；产品重（全模块套件）、贵（企业级订阅数千美元/年起）；隐私政策审查与生成偏模板化；OneTrust 等不支持中文法规条款级对标与 SCC 中文模板比对。
- LegalEye 差异：**中国法优先 + 中文 SCC 官方模板比对 + 出海双向（PIPL 出境合规 + 可选 GDPR 对标）**、轻量、0 起步成本。
- 这是 v0.3 完全缺失的直接竞品层，本版补齐。

**⑤ 通用 LLM 应用平台（Dify / FastGPT / Coze）**
- 不足：无开箱数据合规 agent 流，法务自建门槛高；通用知识库非合规结构化；无图谱推理与交叉校验。
- 真实竞争压力：法律团队用 Dify 可复刻本方案大半。
- LegalEye 优势：opinionated 的合规专用 agent 流与报告格式、数据流图谱、条款追溯、交叉校验——**降低法务搭建门槛是壁垒**。

**⑥ 传统 GRC/CLM（DocuSign CLM、用友/金蝶合规模块）**
- 不足：重、贵、非 AI 原生、UX 差、私有部署痛。
- LegalEye 优势：轻量、AI-native、可 SaaS 可私有化。

## 五、商业模式与成本模型（v1.0 新增）

### 5.1 变现路径（三阶段）
| 阶段 | 模式 | 说明 |
|---|---|---|
| 近期（MVP 后） | **SaaS 订阅** | 按审查任务量分档：免费版（5 次/月，单文件）→ 专业版（¥299/月，联合审查+导出）→ 企业版（¥1,999/月，多席位+权限+审计日志） |
| 中期 | **私有化部署授权** | 强监管行业/大客户：Docker 交付 + 年授权费，数据完全不出境 |
| 远期 | **合规服务导流** | 报告触发人工专家复核/整改咨询，与律所分成 |

### 5.2 成本模型（算得过账）
- **单份隐私政策审查（6 维度 + 一致性 + 报告）**：输入约 8-15 万 token（含知识库检索上下文）、输出约 2-4 万 token；按国内模型主流档位估算 **单份成本约 ¥0.5-3**（以官方实时价格为准，默认走低价档模型，高价值任务可升档）。
- **联合审查（隐私政策+DPA+SCC）**：单组约 ¥2-8。
- **月度成本 vs 收入**：专业版单用户月 30 份任务（含 10 组联合）≈ ¥35-70 token 成本，对 ¥299 订阅价毛利 >75%；免费版限流保护成本。
- **基础设施**：阿里云轻量服务器 2C4G ≈ ¥50-100/月；PostgreSQL 自托管免数据库云费。**单人维护月成本 < ¥100。**

### 5.3 护城河叙事
数据（法规/案例/样本评估集沉淀）→ 专业工作流（合规维度 + 交叉校验方法论）→ 产品（图谱/追溯/重审）。三者叠加，Dify 自建复制成本高、通用 LLM 无能力、国际平台无中国深度。

## 六、产品范围（MVP）

### 6.1 MVP 核心功能（P0）
1. 合规文件上传与解析：隐私政策 / 用户协议 / DPA / SCC，PDF / Word / URL。
2. **多智能体审查流水线**：中心化编排 + 6 维度并行 + 工具调用 + 反思校验。
3. **法条基线知识库**：PIPL / 数据安全法 / 网安法 + GB/T 35273-2020 入库 + pgvector 检索（MVP 核心，前置）。
4. **SCC 官方标准合同比对**：跨境模块逐条比对官方模板。
5. **多文档联合审查**：隐私政策 + DPA + SCC 任意组合，跨文档交叉一致性校验。
6. **数据流知识图谱**：实体/关系抽取 + 出境可达路径推理 + 高风险路径高亮。
7. 四块可视化：聊天（SSE 流式）/ 编排画布（React Flow）/ 数据流图谱（React Flow 复用）/ 监控仪表盘（ECharts）。
8. 账号系统（用户 + 管理员双角色）+ demo 免 Key 模式（注册即用系统默认模型，限流）。
9. 合规报告：在线 HTML + Markdown 导出，**每条结论附法规条款号 + 法规版本 + 整改建议 diff + 置信度 + 是否建议人工复核**。
10. 多模型切换：默认阿里云百炼（国内，数据不出境）；用户自带 Key 支持 OpenAI / Anthropic / DeepSeek。

### 6.2 非目标（MVP 明确不做）
- 不做合规文件起草（仅审查与整改建议）。
- 不做代码级 App 隐私扫描（与代码扫描器赛道区分）。
- 不做电子签章 / OA / ERP / GRC 集成。
- 不做计费支付（订阅计费为商业规划，MVP 不实现）。
- 不做实时多人协作。
- 处罚案例 RAG 第二库、法规变更自动重审、GDPR 对标维度、独立整改多轮迭代列为增强项（P1/P2）。

## 七、典型用户故事与端到端流程

### 7.1 用户故事（出海场景）
作为一家**跨境电商独立站**的数据合规负责人，我在上新站点前上传隐私政策 PDF。系统由合规编排官识别文档类型并动态路由：数据流提取智能体勾勒出"订单数据（姓名/地址/电话）→ 境内支付 → 境外物流商（美国）"的数据流图谱，并推理出**敏感个人信息存在出境可达路径**；跨境传输审查智能体自动判定该场景应走"标准合同（SCC）路径"并比对官方模板，发现文档缺少单独同意与 SCC 备案告知；处理依据/同意机制/敏感信息/主体权利等维度并行审查给出各自的缺陷清单；一致性校验智能体发现**隐私政策声明"数据不出境"与图谱中的出境路径矛盾**；最后合规报告智能体汇总报告——每条结论带法规条款号（如 PIPL 第 39 条第 1 款）、法规版本、风险等级、置信度与整改后的条款 diff。我在聊天界面追问"如果改用香港机房呢"，在数据流图谱看到出境路径高亮，在编排画布看到各智能体的调用关系，在仪表盘看到耗时与 token 消耗。之后我上传 DPA 与 SCC，系统对三份文件做交叉一致性校验，发现 DPA 中列出的境外接收方与隐私政策不一致——这是人工分别审查时最容易漏掉的系统性漏洞。

### 7.2 端到端流程（单文件审查）
1. 登录 → 选择模型（默认百炼 / 自带 Key / demo 免 Key）→ 上传合规文件（PDF/Word/URL）→ 后端解析、清洗、分块。
2. 合规编排官（主控）接收 → 判定文档类型与规模 → **动态路由**确定维度组合 → 分派子智能体。
3. 数据流提取智能体：结构化抽取实体（控制者/处理者/受托方/境外接收方/数据类别）与边（收集/存储/共享/委托/跨境传输/匿名化）→ 构建图谱。
4. 处理依据 ‖ 同意机制 ‖ 委托/共同处理 ‖ 跨境传输 ‖ 敏感信息/未成年人 ‖ 主体权利：**六路并行**，每个智能体按需调用工具（法规检索 / 案例检索 / 图谱查询）。
5. 一致性校验智能体（Critic）：单文档跨维度矛盾检测 + 高风险结论复核。
6. 合规报告智能体：汇总生成结构化报告（条款引用 + 整改 diff + 置信度）。
7. 前端四屏联动：聊天流 / 编排画布 / 数据流图谱（风险高亮）/ 仪表盘。
8. 用户追问、查看图谱、导出 Markdown / HTML。

### 7.3 端到端流程（多文档联合审查，新增）
1. 上传 2-3 份文件（隐私政策 + DPA + SCC 任意子集）并标记关系 → 各文件独立走 7.2 步骤 1-4。
2. **跨文档对齐智能体**（一致性校验智能体的第二个职责）：抽取各文件的关键声明键（数据类别 / 处理目的 / 接收方 / 是否出境 / 保留期限 / 权利响应方式）。
3. 声明键两两比对：同一数据类别在不同文件中的处理者、接收方、出境声明是否一致 → 输出**跨文档不一致项清单**（严重级别）。
4. 报告合并展示：单文件发现 + 跨文档矛盾 + 图谱统一呈现。

## 八、合规审查框架（PIPL 章节驱动的 6 维度，v1.0 重构）

> 维度划分随 PIPL 章节结构（"随法条"，非拍脑袋），每个维度对应明确的条款范围与审查问题集。

| # | 审查维度 | 对应法条范围 | 核心审查问题（节选） |
|---|---|---|---|
| D1 | 处理依据与合法性基础 | PIPL 13 / 14 条 | 每个处理活动是否落入 6 类合法性基础之一；目的限制；告知-同意完整告知要素 |
| D2 | 同意机制 | PIPL 14/16/17、23（向第三方提供）、29（敏感）、39（出境）条 | 单独同意场景识别；同意可撤回；不得以撤回为由拒绝服务（合理情形除外） |
| D3 | 委托处理 / 共同处理 / 转移 | PIPL 20-22 条 | 委托协议要素；受托方义务转述；共同处理连带责任；合并/分立的告知 |
| D4 | 跨境数据传输 | PIPL 38-43 条 + 《数据出境安全评估办法》+《个人信息出境标准合同办法》+ 官方 SCC 模板 | 出境路径判定（安全评估/标准合同/认证）；触发条件核对；单独同意；告知事项；**SCC 模板逐条比对** |
| D5 | 敏感信息与未成年人 | PIPL 28-31 条 | 敏感信息清单对照；单独同意；必要性说明；**未成年人识别与监护人同意机制** |
| D6 | 主体权利保障 | PIPL 44-50 条 | 查询/复制/更正/删除/可携带/撤回同意/自动化决策解释的响应机制、时限与渠道 |
| D7（P1） | 处理者义务 | PIPL 51-58 条 | 安全措施；DPO 任命；PIA 影响评估；安全事件应急；保存期限 |
| D8（P2） | 自动化决策 | PIPL 24 条 | 自动化决策告知、拒绝权、说明义务 |

- **MVP 并行维度：D1-D6**（6 路并行）；D7、D8 作为增强项（同样式接入，可插拔）。
- 每条维度输出统一格式的 `ComplianceFinding`（见第十五章数据模型），保证跨维度可比、可汇总。

## 九、多智能体设计（真 Agent 化，v1.0 核心升级）

### 9.1 设计原则：为什么这是"真多智能体"而非"伪多智能体"
| 伪多智能体（v0.3 形态） | 真多智能体（v1.0 形态） |
|---|---|
| 同一模型 × N 个 prompt，结果互不依赖 | 子智能体拥有**工具集**，自主决定何时检索法规/案例/图谱 |
| 无信息共享，各审各的 | 共享**数据流图谱状态**，图谱查询作为工具被各维度调用 |
| 单次生成即结论，无校验 | **generator → critic 反思循环**：一致性校验智能体复核高风险结论 |
| 固定流水线 | **动态路由**：按文档类型/长度/场景组合维度，编排官决策 |

### 9.2 智能体角色清单（MVP 10 智能体 + 3 工具）
| 智能体 | 类型 | 职责 | 关键输入 | 输出 |
|---|---|---|---|---|
| 合规编排官（主控） | Orchestrator | 文档识别、动态路由、维度组合决策、任务分发、状态管理 | 文件元数据 + 解析文本 | 工作流执行计划 |
| 数据流提取智能体 | Extractor | 实体/关系结构化抽取（规则+LLM 混合），构建图谱 | 文件文本 | 图谱节点边 JSON |
| 处理依据审查智能体 | D1 | 合法性基础映射 | 文本 + 图谱 + 法规检索 | 缺陷清单 |
| 同意机制审查智能体 | D2 | 单独同意/撤回机制核查 | 文本 + 图谱 + 法规检索 | 缺陷清单 |
| 委托共同处理审查智能体 | D3 | 委托/共同/转移条款核查 | 文本 + 法规检索 | 缺陷清单 |
| 跨境传输审查智能体 | D4 | 出境路径判定 + SCC 模板比对 | 文本 + 图谱 + SCC 库 + 案例检索 | 缺陷清单 |
| 敏感信息审查智能体 | D5 | 敏感/未成年人核查 | 文本 + 图谱 + 法规检索 | 缺陷清单 |
| 主体权利审查智能体 | D6 | 权利响应机制核查 | 文本 + 法规检索 | 缺陷清单 |
| **一致性校验智能体（Critic）** | Critic | 单文档跨维度矛盾 + 高风险结论复核 + **多文档交叉一致性** | 全部维度结果 + 图谱 + 多文件声明键 | 矛盾/复核清单 |
| 合规报告智能体 | Reporter | 汇总、条款引用、整改 diff、报告 JSON | 全部结果 | 报告 |

**Agent 工具集（LangGraph `create_react_agent` 风格挂载）：**
| 工具 | 能力 | 使用方 |
|---|---|---|
| `retrieve_law_baseline(query)` | 法规/国标库语义检索，返回条款号+原文+版本 | D1-D8 |
| `retrieve_enforcement_case(query)` | 处罚案例检索（增强项接入后生效） | D4/D5 风险锚定 |
| `query_dataflow_graph(entity, edge_type)` | 图谱查询 + **可达路径分析**（如：敏感信息→境外接收方是否可达） | D2/D4/D5、Critic |
| `compare_scc_template(clause)` | 与官方 SCC 模板逐条比对 | D4 |
| `generate_diff(original, remediation)` | 整改文本 diff | Reporter |

### 9.3 编排流程（LangGraph 状态图，v1.0 扩展）
```
合规编排官(动态路由)
  → 数据流提取(Extractor)
  → [D1 ‖ D2 ‖ D3 ‖ D4 ‖ D5 ‖ D6]  6 路并行，各自按需调工具
  → 一致性校验(Critic) ──有矛盾──> 反馈对应维度修订 ──> 再校验（最多 2 轮）
  → 合规报告(Reporter) → 完成
```
- 状态对象：文件文本、数据流图谱（共享状态，节点可被各 Agent 以工具形式查询）、各维度缺陷、矛盾清单、整改建议、报告。
- **反思循环**：Critic 发现高风险结论依据不足或跨维度矛盾时，将问题打回对应维度 Agent 带上下文重审（有限迭代，防死循环）。
- **动态路由规则**：文档类型（privacy_policy/user_agreement/dpa/scc）决定默认维度组合；超长文档分块审查 + 汇总；多文件上传进入联合审查模式。
- 编排画布直接映射 LangGraph 图结构（节点=智能体，边=数据流），可视化调用关系与当前执行状态。

### 9.4 多模型路由
- 默认 provider：**阿里云百炼**（OpenAI 兼容）——国内模型，数据不出境，契合合规工具的合规性，覆盖未配置 Key 用户与 demo 免 Key 模式。
- 用户自带 Key：OpenAI / Anthropic / 阿里百炼 / DeepSeek。
- 实现：LangChain ChatModel 工厂；百炼/DeepSeek/OpenAI 用 `ChatOpenAI` 指向各自 OpenAI 兼容 endpoint，Anthropic 用 `ChatAnthropic`；LangGraph 节点统一调用工厂。

### 9.5 合规结论结构（统一 schema）
- 合规判定：合规 / 不合规 / 待补 / 不适用。
- 风险等级：高 / 中 / 低（高风险=跨境未合规、敏感信息缺单独同意、跨文档矛盾等）。
- 维度：D1-D8 + 交叉一致性。
- **每条结论强制字段**：违反法规条款号（含版本，如《个人信息保护法》第 39 条第 1 款，2021 版）、置信度、整改建议文本、是否建议人工复核、依据检索片段链接。

## 十、数据流知识图谱与合规推理（创新核心，v1.0 增强）

### 10.1 图谱构建
- 节点：控制者 / 处理者 / 受托方 / 境外接收方 / 数据类别（含敏感标记）。
- 边：收集 / 存储 / 共享 / 委托处理 / 跨境传输 / 匿名化，边携带 `legal_basis`、`is_risk` 属性。
- 抽取策略：**规则（正则 + 关键词词典）与 LLM 抽取双通道**，交叉验证降低幻觉；图谱 JSON 作为共享状态供各 Agent 以工具查询。

### 10.2 合规推理（v1.0 新增：不只画图，还会算）
| 推理规则 | 逻辑 | 输出 |
|---|---|---|
| 出境可达路径 | 图上 BFS/DFS：数据类别（敏感）→（共享/委托）→ 跨境传输边 → 境外接收方，多跳路径枚举 | 高风险路径清单 + 图谱高亮 |
| 未获单独同意的出境边 | 跨境传输边 && 文档无对应单独同意条款 → 风险 | 高风险边 |
| 声明-图谱矛盾 | 文档声明"数据不出境" && 图谱存在跨境边 | 一致性冲突项 |
| 触发安全评估判定 | 依据 100 万人以上个人信息 / 敏感信息 1 万人等阈值，结合图谱数据量信息 | 出境路径建议（安全评估 / SCC / 认证） |
- 实现：`networkx` 构建图 + 规则引擎；前端 React Flow 渲染，高风险路径/边高亮 + 可点击追溯条款。

### 10.3 价值
人工读长文本建不出全局图、算不出多跳路径；通用 LLM 不做图推理；这是 LegalEye 独有的"可解释的合规推理"能力。

## 十一、创新点（v1.0 定稿：5 项核心 + 3 项增强）

**核心（MVP 实现）：**
1. **数据流知识图谱 + 合规推理**：抽取→构图→可达路径分析→风险高亮，唯一把"图"变成"推理引擎"的合规审查方案。
2. **多文档交叉一致性校验**：隐私政策/DPA/SCC 声明键对齐比对，检测跨文档矛盾——单 agent 通吃与人工分审均无法发现。
3. **真多智能体协作闭环**：工具调用 + generator-critic 反思 + 动态路由，多智能体价值可被验证而非装饰。
4. **条款-法规可追溯引用（含版本）**：每条结论精确到条款款号与法规版本，可点击跳转知识库原文；报告标注审查时所依据法规版本。
5. **整改 diff 闭环**：起草整改条款文本 + diff 视图，从"发现"到"整改"闭环。

**增强（P1/P2）：**
6. **法规变更自动重审（P1）**：知识库按生效日期版本化；法规更新入库后，对历史报告做**版本差分影响分析**，自动标出受影响结论并触发重审建议。
7. **处罚案例风险锚定（P1）**：案例库接入后，结论不只判"是否合规"，更标注"此类行为历史上被罚过（案件号+罚额）"。
8. **GDPR 对标维度（P2）**：出海企业常需双法对标，D1-D6 增加 GDPR 条款映射（增强项）。

## 十二、数据来源与知识库工程化（v1.0 补齐落地细节）

### 12.1 法规基线知识库（RAG 主库，MVP 核心，M2 前置）
| 来源 | 内容 | 获取方式（落地细节） | 角色 |
|---|---|---|---|
| 国家法律法规数据库 flk.npc.gov.cn | PIPL / 数据安全法 / 网安法全文 | 官方站点检索导出 + 人工校对条款号；站点 JS 渲染，禁止高频抓取，**优先官方检索下载功能与人工整理**，标注来源与版本 | 最高法律基线，每条结论引用条款号+版本 |
| 全国信息安全标准化技术委员会 | GB/T 35273-2020《个人信息安全规范》 | 官方发布文本；**版权注意：仅本地/私有库使用，不入开源仓库** | 可逐条对照的实操条款标准 |
| 网信办 | 《数据出境安全评估办法》《个人信息出境标准合同办法》+ 官方 SCC 模板（2023 版） | 官方公开文本 + 官方模板 PDF 结构化 | 跨境路径判定依据 + **真实"标准合同"标尺** |

### 12.2 处罚案例知识库（RAG 第二库，P1 增强项）
- 来源：网信办公示执法信息、工信部 App 违规通报、市场监管总局处罚公示、法院公开裁判文书（注意裁判文书网访问收紧，优先官方公示与通报）。
- 结构化：违规事实 + 违反条款 + 处罚结果 + 发生时间。
- 合规性：遵守 robots.txt 与访问频次，仅收集公开公示信息。

### 12.3 法条结构化工程（M2 关键路径）
- 条款结构解析：`第X章 第X条 第X款` → `LawBaseline{statute, article_no, article_text, effective_date, version}`。
- **版本化管理**：每条法条带 `effective_date` 与 `version`；法规修订时新增版本记录而非覆盖（支撑创新点 6 版本差分）。
- 入库脚本：`scripts/ingest_laws.py`（结构化源 → Postgres + pgvector 向量化），幂等可重跑。

### 12.4 测试与评估数据集（金标集，三层评估用）
- **干净样本**：官方/行业公示的隐私政策范本（合规度高）。
- **脏样本（ground truth）**：可控注入违规（删单独同意、虚构境外接收方未走评估、扩大目的范围、**政策与 DPA 声明不一致**等），人工标注每条注入风险。
- **规模**：30 份单文档金标 + 10 组多文档交叉金标（隐私政策+DPA / +SCC），覆盖出海场景（含跨境数据流）。

### 12.5 真实用户输入（运行时）
- 用户上传自有合规文件（PDF / Word / URL）；原文可选不持久化（敏感场景仅内存解析后丢弃）；支持脱敏。

## 十三、三层评估体系（v1.0 重构，替代单薄指标）

| 层 | 评估对象 | 指标（可承诺） | 方法 |
|---|---|---|---|
| L1 抽取层 | 数据流图谱质量 | 实体 F1 ≥ 0.85；关系 F1 ≥ 0.80 | 金标集比对，规则+LLM 双通道 |
| L2 结论层 | 合规判定质量 | 高风险召回 ≥ 90%；误报 ≤ 15%；**条款引用准确率 ≥ 85%** | 金标集；引用准确率独立抽查（错误引用比漏报更致命） |
| L3 报告层 | 端到端质量 | 多文档交叉矛盾检出率 ≥ 80%；报告结构化完整率 100% | 交叉金标集 + LLM-as-judge + 人工抽查 10% 一致性 |

- 评估脚本：`scripts/evaluate.py`，跑金标集输出指标报告；**每次 prompt/工作流改动必跑**，防回归。
- 指标写入项目文档，答辩/评审可现场复现。

## 十四、技术架构（v1.0 定稿：轻量服务器，消除函数计算硬伤）

### 14.1 架构决策记录（ADR）
| 决策 | v0.3 | **v1.0** | 理由 |
|---|---|---|---|
| 部署 | 阿里云函数计算 + OSS | **阿里云轻量应用服务器（2C4G）+ Docker Compose** | 函数计算有实例时长限制、SSE 流式支持存疑，无法承载长任务与联合审查；轻量服务器约 ¥50-100/月，长任务/SSE 无约束，国内访问稳定 |

- 向量检索：pgvector + LangChain `PGVector`（自托管），双库（法规 + 案例）。
- 图谱推理：networkx（BFS/DFS 可达路径）+ 规则引擎。

- 整改 diff：`diff-match-patch` 生成条款级 diff。

## 十六、安全与合规

- **数据不出境**：默认阿里云百炼国内模型；自托管 Postgres/存储均在阿里云国内区；用户切换境外模型时前端提示数据出境风险。
- 用户 API Key：服务端 Fernet 加密存储，调用时解密，绝不返回前端明文。
- 合规文件原文：传输 HTTPS；**原文可选不持久化**（敏感场景仅内存解析后丢弃）；支持脱敏。
- 法规知识库获取：优先官方开放数据源，遵守 robots.txt；GB/T 35273 等版权文本仅私有库使用。
- 鉴权：JWT + 用户/管理员双角色，管理员操作服务端校验；多用户数据隔离（任务/文档按 user_id 过滤）。
- 密钥管理：.env + pydantic-settings，.env 入 .gitignore。
- **免责声明**：系统输出为合规辅助参考，不构成法律意见；报告标注"建议人工复核"项。
